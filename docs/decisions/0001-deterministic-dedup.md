# ADR 0001 — Детерминированный дедуп: механику в код, состояние в памяти Hermes

- **Статус:** Пересмотрено 2026-06-14 — состояние дедупа перенесено в БД на стороне MCP (см. «Дополнение» в конце)
- **Дата:** 2026-06-14
- **Контекст ТЗ:** §4 Level 3 (дедупликация между запросами), §5 (контракт MCP-сервера)

> **TL;DR (после пересмотра):** исходное решение «состояние в памяти Hermes» оказалось
> нерабочим — встроенный инструмент `memory` Hermes **не умеет читать**, поэтому модель не может
> получить `seen_blob`. Состояние дедупа перенесено в **БД (SQLite) на стороне MCP**. Подробности —
> в разделе «Дополнение (2026-06-14): пересмотр».

## Контекст

Дедупликация показанных статей реализована **промптом** skill (`hermes/skills/news/news-digest/SKILL.md`)
поверх встроенной памяти Hermes (`MEMORY.md`). Модель сама выполняет всю бухгалтерию:

- извлекает числовой ID статьи регуляркой из URL (`/articles/(\d+)/`);
- фильтрует кандидатов по буквальному вхождению ID в строку-снапшот;
- объединяет множества `OLD_IDS ∪ SHOWN_IDS`;
- обрезает скользящее окно («последние ~50», «≤2200 символов»);
- дословно воспроизводит старую строку для `memory replace`.

На бесплатной модели (`openai/gpt-oss-120b:free`) эта бухгалтерия нестабильна.

### Корень проблемы

Дедуп — **детерминированная** задача (точная арифметика, операции над множествами,
посимвольное копирование длинных списков), а LLM — **вероятностный** генератор. Усилители
в нашем кейсе: слабая free-модель и длинный агентский проход (к моменту записи снапшот из
раннего шага уже «далеко» в контексте). Промпт уже усилен (`SHOWN_IDS` как единственный
источник правды, строго механическая фильтрация, безусловная запись — git `a1934ec`, `3648014`),
дальше работает закон убывающей отдачи: подробный промпт **снижает частоту** ошибок, но не даёт
**гарантии**.

## Решение

Цель — **детерминированный дедуп** и устранение глюков бухгалтерии.

1. **Механику переносим в код MCP** (детерминированный, тестируемый PHP): извлечение ID,
   фильтрацию по показанным ID, объединение и обрезку окна.
2. **Состояние (показанные ID) остаётся в памяти Hermes.** Модель передаёт его инструменту
   параметром и кладёт обновлённый результат обратно в память — для модели это **непрозрачный
   blob**, который она лишь перекладывает память↔инструмент, без парсинга и арифметики.
3. **Суждение «что считать одной темой» остаётся у модели** — это настоящее смысловое решение,
   не бухгалтерия.

## Доводы за это решение

- **Детерминизм там, где он нужен.** Извлечение ID, множества и обрезка окна в коде дают
  гарантию, а не снижение вероятности ошибки. Это не та работа, где промптинг когда-нибудь «дозреет».
- **Не конфликтует с ТЗ и архитектурой.** Состояние по-прежнему живёт в памяти Hermes →
  требование L3 «через память Hermes» соблюдено. MCP не хранит состояние между вызовами →
  принцип stateless-MCP сохранён. Поэтому, в отличие от полного серверного дедупа, это решение
  **не отменяет** документированную оговорку и не требует переписывать трактовку ТЗ.
- **Skill проще и дешевле.** Из промпта уходит самая хрупкая и многословная часть → меньше
  токенов на запрос (важно при free-лимите ~20 req/min) и проще поддержка.
- **Тестируемость.** Логика дедупа покрывается юнит-тестами рядом с остальным кодом MCP.

## Границы (scope)

**В scope:** глюки бухгалтерии — извлечение ID, операции над множествами, обрезка окна,
дословный `replace`.

**Вне scope (известные ограничения, не закрываются этим решением):**

- **Гонки** при параллельных запросах одной темы/чата (read-modify-write памяти) — следствие
  того, что состояние осталось в памяти Hermes; осознанный размен ради соблюдения L3.
- **Контентные дубли** — тот же сюжет под другим ID (перепечатка, перевод): id-дедуп их не ловит
  ни в промпте, ни в коде; нужен семантический дедуп — отдельная задача.
- **Рассинхрон ключа** по формулировке темы («AI/ML» vs «машинное обучение») — вопрос
  нормализации ключа, отдельно от бухгалтерии.

## Рассмотренные альтернативы

- **Полный серверный дедуп с состоянием в MCP.** Максимальный детерминизм и попутно решает гонки,
  но нарушает L3 «через память Hermes» и принцип stateless-MCP, требует хранилища на сервере и
  переписывания трактовки ТЗ. Отвергнут: гонки вне scope, цена не оправдана.
- **Только усиление промпта / сильная платная модель.** Минимум работы, ноль конфликта с ТЗ, но
  **не даёт детерминизма** — а цель именно он. Отвергнут.
- **Минимум: сервер отдаёт готовый `id`, остальное на модели.** Убирает лишь парсинг URL;
  фильтрация, объединение и запись остаются на модели → дедуп по-прежнему «у модели». Отвергнут
  как половинчатый.

## Последствия

- **+** Бухгалтерия дедупа детерминирована и покрыта тестами.
- **+** Решение совместимо с L3 и stateless-MCP; README-оговорка про серверный дедуп остаётся верной.
- **+** Короче и дешевле промпт skill.
- **−** Появляется новый контракт инструмента MCP (параметры/возврат); на модели остаётся
  минимальная ответственность — корректно прокинуть blob память↔инструмент.
- **−** Гонки и контентные дубли остаются открытыми (см. «Границы»).

## Дополнение (2026-06-14): пересмотр — серверный дедуп с БД

При **живой проверке** (Hermes CLI `-z` / `chat -v`, free-модель `gpt-oss-120b:free`) исходное
решение (состояние в памяти Hermes, модель перекладывает blob) оказалось **нерабочим**.

### Найденные факты

- **Встроенный инструмент `memory` Hermes не умеет читать.** Операции — только `add`/`replace`/`remove`
  (`agent/memory_manager.py`, `on_memory_write(action, target, content)`); read/get/search-by-key нет.
  Память доходит до модели лишь **авто-инъекцией** в системный промпт (`build_system_prompt()`,
  `prefetch_all(user_message)`, блоки `<memory-context>`) — это семантический recall, а не точное
  чтение строки по ключу.
- **Поэтому модель не может получить `seen_blob`.** В трейсе (`.log/2026_06_14_diag_run2_verbose.log`)
  модель рассуждает: *«memory tool only add/replace/remove… can't read… call dedup_filter with
  seen_blob empty»* — и зовёт `dedup_filter` с `"seen_blob": ""`. Сравнивать дедупу не с чем.
- **`replace` без чтения невозможен:** `memory` вернул `"old_text is required for 'replace' action"` —
  чтобы обновить строку, нужен старый текст, а прочитать его нельзя (Catch-22).
- Итог двух реальных прогонов: `dedup_filter`/`dedup_commit` (детерминированный код) **вызываются и
  работают**, но получают пустой вход, и их результат негде сохранить так, чтобы модель потом прочла.

### Вывод

Ключевое допущение исходного решения — «модель читает `seen_blob` из памяти Hermes» — **физически
невыполнимо** в Hermes. Хранить состояние дедупа в памяти Hermes нельзя.

### Новое решение (B) — состояние дедупа в БД на стороне MCP

- `dedup_filter(key, candidates)` и `dedup_commit(key, shown_ids, keep)` **сами читают и пишут**
  своё хранилище — **SQLite-файл в volume MCP-сервера**; ключ — `digest:<chat_id>:<тема-slug>`.
- Модель передаёт только **`key`** (+ кандидатов / показанные `id`). Никакого `seen_blob`, никакой
  работы с памятью Hermes.
- MCP становится **stateful** (volume под БД) — принцип stateless-MCP осознанно снят.

### Влияние на ТЗ и прежние «Доводы»/«Последствия»

- **L3** трактуем по **намерению** («между запросами не повторять материалы»), а не буквально
  «через память Hermes»: буквальный механизм в Hermes невозможен (см. факты). Cross-request дедуп
  достигается, состояние — в БД MCP.
- Прежний довод «не конфликтует с ТЗ / stateless-MCP» **отозван**. Прежняя «отвергнутая
  альтернатива — полный серверный дедуп» теперь **принята**.

### Что улучшается

- **Гонки решены:** read-modify-write атомарен на стороне MCP (транзакция в `dedup_commit`).
- Дедуп **детерминирован end-to-end** и не зависит от способности модели читать память.
- Skill проще: модель лишь строит `key` и зовёт инструменты.

### Остаётся вне scope

- Контентные дубли (тот же сюжет под другим `id`) и рассинхрон ключа по формулировке темы.
